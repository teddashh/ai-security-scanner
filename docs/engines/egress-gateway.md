# Managed egress gateway

A policy-bound SOCKS5 gateway between engine containers and everything outside them. Naabu, httpx, Nuclei, Greenbone and ZAP reach approved targets through it (e8d9e96), and the five cloud and two Microsoft 365 engines reach provider endpoints through it (e4571df). **Scans run the digest-pinned image named in `runtime/managed-egress-gateway.json`, not the Rust source in this tree.** The desktop must keep reading the status document that pinned image writes.

## Local build and update entry

Build from the repository root with [this Dockerfile](../../engines/images/egress-gateway/Dockerfile) and context `.`. No host `.engine-cache` preparation is required. The Rust library embeds files outside `src-tauri/src`; preserve the COPY list and its contract tests when those inputs change.

See the [image build index](image-build-index.md) for local build commands and the update record. A local gateway build does not change the runtime pin or authorize its publication.

## How it is wired

- **Image selection.** `managed_egress_gateway_spec()` (`src-tauri/src/gateway_release.rs`) embeds the manifest and requires schema 1.0.0, `product_version` equal to the app version, the release repository, a tag equal to both `GATEWAY_PUBLICATION_TAG` and `"{version}-1"`, a 40-hex source revision and a sha256 digest. The desktop (`provision_execution_network` in `commands.rs`) and the CLI use it; if it fails, network checks are blocked with `EgressGatewayUnavailable`. The image is pulled as `repository@digest` (`ensure_gateway_container_image`, 10-minute timeout). The `ai-security-scanner-egress-gateway` sidecar listed in `src-tauri/tauri.conf.json` is not on this path.
- **Provisioning** (`provision_container_policy`). An internal network `ass-egress-<id>`, an uplink network `ass-uplink-<id>` on a subnet that avoids the internal one, and the container `ass-gateway-<id>` created on the uplink with `--pull=never --read-only --cap-drop=ALL --security-opt=no-new-privileges:true --pids-limit 64 --memory 128m --cpus 0.500 --restart=no --log-driver=none`, an 8 MB `/tmp`, the policy mounted read-only and the status directory read-write. `network connect --ip <listener-ip>` then joins it to the internal network. Readiness waits up to 5 s for `ready`/`ready`.
- **Engines.** Scanner containers join only the internal network, with every proxy variable set to `socks5h://<gateway-ip>:1080` and `NO_PROXY` empty (`container_runtime.rs`). Nuclei receives `socks5://` ([nuclei.md](nuclei.md)), Naabu `<gateway-ip>:1080` ([naabu.md](naabu.md)), and ZAP reads the gateway from its plan ([zap.md](zap.md)). The cloud launcher runs a loopback HTTP CONNECT proxy that opens each tunnel through the gateway (at most 8 tunnels, 20 new per second, port 443; [cloud-launcher.md](cloud-launcher.md)), and the Microsoft 365 launcher hands PowerShell `socks5://` (e4571df; [m365-launcher.md](m365-launcher.md)).
- **Policy** (`EgressGatewayPolicy`, schema 2.0.0, `deny_unknown_fields`). `from_resolved_plans` serves approved targets: the strictest concurrency, connections per second and timeout across at most 128 grants, connect timeout capped at 120 s, the frozen hostname and addresses, no destination inside the scanner bridge, expiry within 24 h. `from_provider_service_plan` serves provider endpoints: 10 concurrent, 25 connections/s, 30 s connect, 300 s per connection, port 443 only, no sensitive or metadata addresses, expiry within 1 h. Both allow at most 10,000 address-port pairs.
- **Behavior** (`egress_gateway.rs`). No-auth SOCKS5 CONNECT only. A hostname connects only to its frozen addresses; there is no live DNS. Replies: 2 for a destination outside the policy or no rate slot before the connect deadline, 5 or 6 for connect failure or timeout, 7 for a non-CONNECT request, 8 for an unsupported address type. A peer outside the allowed client network is dropped without a reply. A connection over the rate waits for a slot (84bde80). The bound is on connections, not requests, so a keep-alive engine can exceed its declared request rate (28b1843).
- **Status contract.** `status.json` is at most 1,024 bytes and written at most once per second. The pinned image writes schema 1.1.0, for example `{"schema_version":"1.1.0","phase":"ready","code":"ready","refusals":{"rate":0,"destination":0,"unauthorized_client":0}}`. `read_opened_gateway_status` accepts exactly 1.0.0 without refusals and 1.1.0 with them, each with strict phase and code pairs; anything else fails closed.
- **Coverage.** Cleanup turns the final status into `GatewayRefusalRecord::Counted`, or `Unavailable` when no status could be read; a 1.0.0 status yields no record. `append_gateway_refusal_gaps` adds "connections refused by the rate limit" (Truncated), "destination outside the approved scope" (record note) and "unrecorded connection refusals".

## Downstream changes

None; this is project code. Its known limit is the connection-based rate bound, which is the third ZAP blocker.

## Lessons from real runs

- 2026-09-17: the image build failed with "couldn't read `src-tauri/src/../../docs/research/augustus-single-destination-profile.json`" -> the Dockerfile copies every library embed, and a test derives the list (18b7313).
- 2026-09-25: with the bound at 5 connections/s, 5 of 124 pages were fetched and the engine still reported success -> three refusal counters in status schema 1.1.0 and a `stopped` code (d99114a), then `GatewayRefusalRecord` and coverage rows instead of collapsed cleanup prose (e8d9e96).
- 2026-09-25: a denied destination was closed without a reply, which ZAP reported as "Malformed reply from SOCKS server" -> reply 2 (1a2dbb2).
- 2026-09-25: Nuclei lost 210 requests to rate refusals (635 of 853 reached the target) -> over-rate connections wait: 0 refused, 845 of 853 reached (84bde80).
- 2026-09-25: after d99114a the desktop reader accepted only 1.1.0 while the pinned image (built from 12f0279) wrote 1.0.0, so every website and internal-system check failed with "gateway status was malformed" -> the reader accepts both exact shapes (b097145).
- 2026-09-25: Docker Engine 29 reports "network <selector> not found", so subnet retry aborted with "gateway uplink inspection failed" when the first uplink candidate overlapped Docker's default bridge -> that reply is recognized (8f30d31).
- 2026-09-25: a cleaned website or internal-system check stayed at "Queued 0%", logging "a terminal checkpoint can only be retried with a higher attempt number" -> retry clears the ended attempt's network identity (8de162e).
- 2026-09-30 to 2026-10-01: moving the product to 0.3.0 forced tag `0.3.0-1` while the manifest still carried the `1.0.0-1` digest (1614d72); the publication smoke expected status 1.0.0 and failed on the 1.1.0 the image writes -> a CI test binds the smoke to `STATUS_SCHEMA_VERSION` (69b54ab); the image was published from a493929 and pinned (f37da61).
- 2026-10-02: botocore read `socks5h://` as an HTTP proxy, CloudQuery's Go 1.19 build rejected the scheme, and .NET ignored it -> the launcher-side bridges above; the gateway itself did not change (e4571df).

## Updating this engine

- **Know what runs.** The manifest's `source_revision` is a493929. Run `git log a493929..HEAD -- src-tauri/src/bin/egress_gateway.rs src-tauri/src/bin/egress_probe.rs src-tauri/src/managed_network.rs engines/images/egress-gateway`; today only f37da61 (the manifest pin) is newer. A source change does nothing for scans until the image is republished and its digest pinned.
- **Keep reading what the pin writes.** Change the status reader only together with a published, pinned image, and test it with that image's exact bytes (b097145): `readiness_reads_the_pinned_gateway_status_schema`, `gateway_status_accepts_exactly_the_two_recognized_schemas`, `the_pinned_gateway_image_status_is_read_without_refusal_counts`, `stopped_status_code_is_an_accepted_terminal_pair`.
- **Policy changes.** The pinned gateway parses `EgressGatewayPolicy` from its own build with `deny_unknown_fields` and requires schema 2.0.0. Publish and pin a gateway that accepts a new field before the desktop sends it.
- **Version and tag.** The manifest must carry the app's version and tag `"{version}-1"`, or every network check is blocked. Update both in the same commit as a version change, then publish and pin the digest (1614d72 to f37da61). `0.3.0-1` appears in the workflow (`concurrency.group`, `IMAGE_TAG`), `runtime/managed-egress-gateway.json`, `GATEWAY_PUBLICATION_TAG` in `gateway_release.rs`, `scripts/release/verify-publication-artifact.mjs`, `tests/release/verifyPublicationArtifact.test.mjs`, four self-test values in `scripts/engine-image-evidence.mjs`, and this page.
- **Build and tests.** A new embed outside `src-tauri/src` needs a COPY line; `tests/ci/managedEgressGatewayWorkflow.test.mjs` derives the list. The `cli` gate never compiles the gateway, so `.github/workflows/ci.yml` runs clippy and tests with `--features egress-gateway` (lines 180 and 181). Key tests: `frozen_hostname_never_performs_live_dns_resolution`, `metadata_and_unapproved_ports_are_denied`, `a_connection_over_the_rate_waits_for_a_slot_instead_of_being_refused`, `a_denied_destination_answers_with_a_refusal_before_closing`, `refusal_counts_round_trip_within_the_status_bound`, `cleanup_records_gateway_refusal_counts_or_their_absence`, `recovery_reads_the_refusal_record_before_removing_it`, `embedded_manifest_returns_only_a_digest_qualified_image`.
- **Other workflows build their own gateway.** `engine-image-greenbone.yml` runs Greenbone behind a gateway built from the tree (`target/debug`), so a passing Greenbone publication says nothing about the pinned image.
- **Verify the pinned image.** Repeat the workflow smoke against the pinned digest: an internal bridge network, a 2.0.0 policy with documentation addresses, the exact ready status above, then the probe (`--entrypoint /usr/local/bin/ai-security-scanner-egress-probe`) reporting `socks5_no_connect_greeting` with `gateway_reachable` true and `upstream_connect_attempted` false. For engine behavior, run a website check in the desktop against `<local-test-origin>` and read the refusal counts in the run's cleanup detail.
