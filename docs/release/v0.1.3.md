# v0.1.3 one-click Windows setup pre-release

> **Historical / non-normative release-line record.** This file preserves claims and plans written for this version line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.3` is the next installable public preview on the way to stable `v0.2.0`. It focuses on the
Windows first-run problem found during hands-on testing: the app no longer makes a newcomer open an
Administrator PowerShell window just to prepare WSL 2.

## What changed

The actions below describe the `v0.1.3` UI, not the current first-run contract. The current signed
installer performs fixed prerequisite detection/preparation when needed; after installation or
restart, the main shell opens and product-runtime work continues automatically in the background.
There is no later beginner-facing WSL Repair journey.

- **Fix this for me / 交給程式處理** was the primary action when WSL 2 was missing, disabled, or
  outdated.
- Windows showed its standard administrator confirmation once. After approval, the app waited for
  Windows, checked the result, and continued its setup journey automatically.
- A required restart became the only next step. The app did not restart Windows automatically or
  begin the managed-runtime image download before Windows was ready.
- This historical build kept manual Microsoft commands under **Other ways / 其他方式**. They are
  not a fallback in the current beginner path; maintainer diagnostics remain outside the first-run
  UI.
- The same plain-language action and progress state appeared in both the setup page and sidebar, in
  English and Traditional Chinese.

## Narrow administrator boundary

The repair command accepts no executable, parameters, or operation from the webview. The backend
derives one allowlisted action from the exact current failed prerequisite and runs only the
Windows-owned `System32\wsl.exe` with fixed `--install --no-distribution` or `--update` arguments.
It does not invoke PowerShell or `cmd.exe`, elevate a project helper, receive the administrator
password, install a Linux distribution, or restart the computer.

## Historical testing status

The preview retained the existing exact-scope security assessment workflow, local cases, evidence,
and provenance. Its GitHub channel published it only after the tagged cross-platform installer and
fresh-host qualification workflow passed. Fresh hosted jobs on Ubuntu 24.04 and Windows 2025 were
required to complete managed-runtime install, real machine start, the fixed network-disabled
Gitleaks container probe, stop, purge, and private-state cleanup.

This was the `v0.1.3` channel policy, not a current global release gate. Present qualification
accepts or withholds each exact installer/platform independently and cannot substitute a modeled
runtime probe for the installed-Windows beginner human path.

The macOS 15 Intel job was required to install the DMG, verify the app and every companion
executable, match the bundled runtime manifest to the release copy, launch the desktop, detach the
DMG, and remove its test state. Its managed-runtime and container lifecycle was recorded as
`not_observed`, not passed,
because GitHub-hosted macOS does not support the nested virtualization required by AppleHV. This
limited evidence was accepted only for that pre-release; its stable-release plan still required
real Mac runtime lifecycle evidence.

It remained a pre-release for hands-on testing. Its planned IAM-newcomer study and deferred formal
QC/code-review sequence are historical; current Windows acceptance starts with the exact installed
localhost human path, while AWS evidence qualifies only the Advanced AWS feature.
