# v0.1.7 hands-on Windows reliability pre-release

> **Historical / non-normative release-line record.** This file preserves claims and plans written for this version line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.7` carries the Candidate 11 product repairs produced by operating the real Windows app
end to end, then extends them across the shared scan lifecycle instead of treating each broken
screen as an isolated exception.

## What feels different

- First launch recognizes prerequisites that are already available and prepares the private scan
  tools before presenting a scan as ready.
- Public and internal network checks accept an IP address or domain. A domain is resolved once,
  its exact addresses are frozen into the run, and the port inventory stays within the selected
  target and bounded common-port preset.
- Scan listeners are attached before startup reconciliation, so fast startup, progress, failure,
  and completion events cannot disappear between screens.
- A stopped scan keeps the evidence already saved, distinguishes a safe retry from a fresh run,
  and offers a redacted technical log without exposing targets, paths, secrets, or raw scanner
  messages.
- Project snapshots keep files when trusted ignore-rule evaluation is unavailable. Files are
  retained rather than silently omitted, while the snapshot remains bounded and read-only.
- AI app and agent checks reuse the code, secret, package, and deployment routes. Applicable
  findings can carry AIDEFEND references alongside NIST CSF and ISO 27001 references.
- Gitleaks is included as a pinned, network-disabled managed engine. VibeScan informed the guided
  workflow and result-envelope design but is not bundled or executed.
- Trivy now uses the input that the user actually selected: repository and IaC snapshots scan
  recognized language-package manifests, while validated OCI layouts scan recognized OS packages.
  Grype remains the complementary OCI language-package and JAR archive check.

## Recovery and cleanup

Windows runtime recovery never treats an old initialization marker as deletion authority. A stale
journal is never permission to delete WSL state. The app may remove only the exact managed machine
that it can still prove it owns; an unexpected surviving WSL distribution produces clear manual
recovery guidance instead of an automatic unregister operation.

## Release qualification

Fresh Linux and Windows installer jobs exercise the managed runtime, fixed private gateway, and
network-disabled Gitleaks container probe. The fixed gateway probe exchanges only a SOCKS greeting
and never sends CONNECT. Windows MSI and Windows NSIS Setup are qualified independently.

The macOS 15 Intel job verifies the installed app, its companion executables, and packaged runtime
manifest. Its managed-runtime lifecycle and network-disabled Gitleaks container probe are recorded
as `not_observed`, not passed because the hosted environment does not provide the nested
virtualization required by AppleHV. This limited evidence is accepted only for a pre-release.

The Linux desktop bundle still receives `glib 0.18.5` through Tauri's GTK3/WebKitGTK stack. That
version is covered by [RUSTSEC-2024-0429](https://rustsec.org/advisories/RUSTSEC-2024-0429.html),
an unsoundness in `VariantStrIter`. Static review found no product or downloaded production
dependency call to the affected iterator API, and the Windows and macOS dependency trees do not
contain this crate. The alert therefore remains open as a Linux dependency-level pre-release risk;
it is not presented as fixed or as a clean dependency scan. The GTK stack cannot move directly to
the first patched `glib 0.20.0`, so a reviewed backport or upstream stack migration remains follow-up
work.

Apple Developer ID signing, notarization, and Windows Authenticode are not configured for this
preview, so the operating system may show an unidentified-developer warning. Updater payloads use
the separate release signing key and must pass the checked-in integrity and provenance workflow.
