# v0.1.2 public testing pre-release

> **Historical / non-normative release-line record.** This file preserves claims and plans written for this version line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.2` was an installable public preview for the then-current bilingual product flow. It exposed
a separate one-time scan-tool setup before guided use cases, cloud connection, progress, results,
export, and comparison. That setup-first journey is superseded: the current product opens the
workspace and prepares disposable scan tools automatically behind the selected task.

## What changed for hands-on testing

- English and Traditional Chinese now cover the complete UI and both README entry points.
- The first layer leads with websites, public IPs, internal IT, source code, cloud, containers, and
  Kubernetes instead of scanner names and engineering contracts.
- Technical identifiers, protocols, engine state, hashes, and detailed limits remain available in
  expandable second-layer details.
- Cloud setup leads with one non-secret connection file from IT, followed by the provider's official
  sign-in page; manual identifiers remain available as a secondary path.
- The historical UI called recommended checks a third setup step. Current work starts from a use
  case, persists the requested run/tasks, and keeps runtime preparation and engine details behind
  that task rather than reviving a setup funnel.
- This preview probed WSL from its setup journey. The current Windows contract assigns fixed WSL
  detection/preparation to the signed installer, opens the main shell, and never asks a beginner to
  administer WSL when preparation fails.

## Existing execution scope

The preview retains typed immutable snapshots for repository, IaC, OCI image-layout, Kubernetes
manifest, and node-configuration inputs. Provider execution remains bound to one exact AWS account,
Azure subscription, GCP project, or Microsoft 365 tenant. Existing local cases, cleanup obligations,
evidence snapshots, and provenance remain intact.

## Historical pre-release qualification

The `v0.1.2` release workflow rebuilt and installed Linux x86-64, universal macOS, and Windows
x86-64 packages from the exact tag, verified updater signatures and complete checksums, and
published build-provenance attestations. Its fresh hosted qualification jobs on Ubuntu 24.04,
macOS 15 Intel, and Windows 2025 were each required to complete managed-runtime install, real
machine start, the fixed network-disabled Gitleaks container probe, stop, purge, and private-state
cleanup.

That all-platform wording describes the historical `v0.1.2` channel. Current acceptance is scoped
to each exact artifact, platform, installer, engine, and claimed feature; one unavailable sibling
does not block an independently qualified artifact.

The numeric `0.1.2` product version is intentional: it sorts after the current `0.1.1` stable build
and before the planned `0.2.0` stable build in Windows MSI, Debian, RPM, macOS, and Tauri updater
version rules. GitHub still labels this build as a pre-release, and it does not become Latest.

This pre-release was intended for hands-on testing. It did not claim completion of its planned
IAM-newcomer study, formal QC, or code review. Under the current policy, missing AWS usability
evidence limits only the Advanced AWS claim; it is not a universal product gate. Apple Developer
ID, Apple notarization, and Windows Authenticode were not configured, so the operating system could
show an unidentified-developer warning even though updater signatures, checksums, and GitHub
attestations verified the published bytes.
