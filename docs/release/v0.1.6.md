# v0.1.6 managed scan connection repair pre-release

`v0.1.6` fixes the local scan connection that could repeatedly appear ready and then stop as soon
as an external-IP or internal-network check began. The gateway now runs beside the scanners inside
the private managed runtime, so Windows no longer asks a native process to listen on an address
that exists only inside WSL.

## What feels different

- Local network checks use one gateway container attached to a private scanner network and a
  separate uplink network. Scanners can reach it without exposing their private network directly.
- Readiness comes from the running gateway itself. A stale desktop status cannot turn a failed
  gateway into a green Ready message.
- If gateway setup fails, the scan keeps the concrete failure and cleanup result instead of sending
  the user through an unexplained Ready/Repair loop.
- The release test installs and exercises Windows MSI and Windows NSIS Setup independently, so the
  downloadable Setup executable receives the same runtime coverage as the MSI.

## Release qualification

Fresh Linux and Windows installer jobs start the real bundled managed runtime, create the production
internal scanner network and dual-network pinned gateway container, wait for its ready status, and
run a second internal-only container from the same pinned image. That probe exchanges only the
SOCKS greeting needed to prove scanner-side reachability, never sends CONNECT, and cannot make an
upstream connection. It then removes the exact probe, gateway, internal network, uplink network,
policy, and status directory; any remaining resource or false cleanup claim fails the release.
The matching recovery record must also be gone before the qualification can pass.

The same jobs also run the existing network-disabled Gitleaks container probe and the full managed
runtime install, start, stop, and uninstall lifecycle. Windows MSI and Windows NSIS Setup run as
separate qualifications on fresh Windows machines.

This is a public testing pre-release on the way to `v0.2.0`. The macOS 15 Intel job verifies the
installed app, its companion executables, and its packaged runtime manifest. Because the hosted Mac
cannot run the required nested virtualization, the managed-egress probe, network-disabled Gitleaks
container probe, and every runtime operation are recorded as `not_observed`, not passed.

This limited evidence is accepted only for a pre-release; a stable release still requires a real
managed-runtime lifecycle on a suitable Mac.

Formal QC and code review remain scheduled after the full product workflow has been exercised end
to end, as planned.
