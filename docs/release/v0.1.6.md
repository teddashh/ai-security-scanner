# v0.1.6 managed scan connection repair pre-release

> **Historical / non-normative release-line record.** This file preserves claims and plans written for this version line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.6` fixes the local scan connection that could repeatedly appear ready and then stop as soon
as an external-IP or internal-network check began. The gateway now runs beside the scanners inside
the private managed runtime, so Windows no longer asks a native process to listen on an address
that exists only inside WSL.

## What feels different

- Local network checks use one gateway container attached to a private scanner network and a
  separate uplink network. Scanners can reach it without exposing their private network directly.
- Readiness comes from the running gateway itself. A stale desktop status cannot turn a failed
  gateway into a green Ready message.
- If gateway setup fails, the scan keeps the concrete failure and cleanup result instead of sending
  the user through an unexplained Ready/Repair loop.
- The release test installs and exercises Windows MSI and Windows NSIS Setup independently, so the
  downloadable Setup executable receives the same runtime coverage as the MSI.
- Code written by a person or generated with AI uses the project-managed Gitleaks 8.30.1 source
  build. Its fixed launcher scans the current worktree with scanner-owned rules, ignores
  repository-controlled suppressions, treats a detection as a finding rather than a crashed scan,
  and redacts secret values before they can enter evidence.
- A new **AI app or agent** starting point runs the existing code, secret, dependency, and deployment
  checks without adding setup steps. Applicable AI-system findings can now carry selected AIDEFEND
  references beside the existing NIST CSF and ISO 27001 references.

VibeScan was evaluated as a vibe-coding workflow reference but is not wrapped or shipped. Its
guided journey and common-results-envelope ideas are reimplemented independently over the existing
Semgrep, Gitleaks, TruffleHog, Checkov, KICS, and Trivy engines. The pinned review and reasons are in
[`docs/research/vibescan-evaluation.md`](../research/vibescan-evaluation.md).

## Historical release qualification

Fresh Linux and Windows installer jobs for `v0.1.6` started the real bundled managed runtime,
created the production internal scanner network and dual-network pinned gateway container, waited
for its ready status, and ran a second internal-only container from the same pinned image. That
probe exchanged only the SOCKS greeting needed to prove scanner-side reachability, never sent
CONNECT, and could not make an upstream connection. It then removed the exact probe, gateway,
internal network, uplink network,
policy, and status directory; any remaining resource or false cleanup claim fails the release.
The matching recovery record must also be gone before the qualification can pass.

The same jobs also run the Gitleaks container probe with a read-only workspace and root filesystem,
no network, the scanner-owned configuration, fully redacted evidence, and exact cleanup, followed
by the full managed runtime install, start, stop, and uninstall lifecycle. Windows MSI and Windows
NSIS Setup run as separate qualifications on fresh Windows machines. The release does not claim a
final Gitleaks image digest or publication evidence until that image's managed publication workflow
has succeeded.

This was a public testing pre-release on the way to `v0.2.0`. The macOS 15 Intel job verified the
installed app, its companion executables, and its packaged runtime manifest. Because the hosted Mac
could not run the required nested virtualization, the managed-egress probe, network-disabled
Gitleaks container probe, and every runtime operation were recorded as `not_observed`, not passed.

That historical channel accepted this limited evidence only for a pre-release and planned to
require a real managed-runtime lifecycle on a suitable Mac for its stable release. This is not a
current cross-platform gate: a failed or unobserved artifact/capability remains unavailable without
withholding independently qualified siblings.

The note's deferred formal QC/code-review sequence is historical and does not replace the current
human-path-first acceptance order.
