# Archived v0.2.0 product-completion proposal

> **Historical / non-normative release-plan snapshot.** This file preserves claims and plans written for this proposed release line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

Terms such as “required,” “must,” and “product completion” below describe the archived proposal
only. They are not current requirements and must not be copied into code, CI, schemas, validators,
or another document. In particular, the proposal's all-platform qualification and 21-engine
framing do not override artifact-scoped release acceptance, independently admitted engines,
partial results, or the installed-Windows first-value path in the canonical specification.

This snapshot proposed `v0.2.0` as a product-completion release line for the local-first assessment
workflow. It aimed to keep
existing cases and historical evidence intact while adding typed target intake, exact provider
scope, and immutable execution contracts across the required scanner families. A source checkout
or version string was never proof that the release shipped. None of the qualification claims below
is current evidence that a platform, engine, installer, or journey passed.

## Typed local targets and durable evidence

- Repository, IaC, OCI image-layout, Kubernetes manifest, and node-configuration inputs use
  explicit input profiles instead of an ambiguous shared directory contract.
- The backend validates each selected target, creates a private immutable snapshot, records its
  digest and source identity, and gives an engine only the mount and profile declared by its plan.
- OCI layouts are checked as a closed, single-image graph with bounded manifests, configs, layers,
  tar entries, uncompressed bytes, and exact diff IDs before Trivy or Grype receives them.
- Coverage and case exports retain raw evidence, adapter and engine provenance, completeness
  issues, and the distinction between a completed empty check, unknown scope, partial capture, and
  a passing result.

## Exact provider scope

- AWS Organizations discovery is bound to one Organizations-enabled caller source. Each scanner
  execution still requires an exact short-lived caller identity for the selected AWS account;
  organization enumeration alone never authorizes a member account.
- Azure discovery and execution are bound to one exact tenant and an `Enabled` subscription.
- Google Cloud discovery walks the bounded active folder/project hierarchy under one exact
  organization, then splits approved scope into one exact active project per execution.
- The managed Prowler wrapper exposes separate AWS-account, Azure-subscription, and GCP-project
  profiles with provider-specific identity preflight and fixed endpoint closure. CloudQuery,
  Steampipe, ScoutSuite, and Cloudsplaining remain AWS-only; upstream feature names do not widen
  their released scope.
- Microsoft 365 remains one exact tenant per source and execution capability. Bootstrap credentials
  never enter scanner containers.

## Archived engine-integration proposal

- The proposal listed 21 engine records. It expected each engine actually offered as runnable to
  bind its own immutable image digest,
  launcher profile, adapter, evidence path, coverage behavior, license disposition, and
  verification path. One unavailable or unqualified engine was not evidence that its siblings
  were unavailable. Scanner images remained separate artifacts and were not bundled in desktop
  installers.
- The proposal expected managed images to publish Linux AMD64 and ARM64 indexes with
  platform-specific SBOM and provenance evidence. Gitleaks and KICS were listed as upstream-image
  exceptions.
- Trivy's fixed offline profiles cover recognized language-package manifests in repository and IaC
  working trees, including supported Java manifests such as `pom.xml`, and recognized OS packages
  in validated OCI layouts. Dependencies discoverable only from JAR contents stay excluded; Grype
  supplies the complementary offline OS/language-package and JAR archive path for OCI images.

## Superseded Windows setup proposal

This proposal used a later **Fix this for me** screen and retained manual Microsoft commands under
**Other ways**. That UI is not the current product direction. The signed installer owns fixed WSL
detection/preparation and normal UAC when Windows requires it; restart state survives, the main
shell opens, and private runtime preparation resumes automatically behind the selected task. A
beginner is never sent to Terminal, a manual WSL fallback, or a second Repair/setup journey.

## Archived upgrade and qualification proposal

Existing local cases, cleanup obligations, evidence snapshots, and provenance are retained across
the application update. Baseline comparisons remain conservative whenever engine, adapter,
ruleset, input, or completeness provenance is not comparable.

The archived workflow proposal rebuilt Linux x86-64, universal macOS, and Windows x86-64 packages
from an exact tag, checked updater signatures and checksums, and produced build-provenance
attestations. It also proposed hosted qualification jobs for Ubuntu 24.04, macOS 15 Intel, and
Windows 2025. That global matrix is not a current cross-platform release gate: present publication
must qualify only the exact artifact/platform/channel being offered, while an unavailable sibling
artifact stays unavailable. The current Windows beginner acceptance path is the installed
localhost journey in the canonical specification; an old AWS/IAM study cannot substitute for it.

The proposal's Linux fixture was intended to check that its manifest-bound QEMU exposed the
`vhost-user-fs-pci` device used by the managed VirtioFS application-data mount. Its Windows fixture
was intended to inspect the proposed Podman WSL namespace before the first provider command. These
were narrow implementation checks, not beginner-journey evidence and not conditions for publishing
an unrelated artifact.

At the time of this snapshot, Apple Developer ID, Apple notarization, and Windows Authenticode were
not configured, so operating systems could show an unidentified-developer warning. Current
signing, updater, checksum, SBOM, and attestation availability must come from exact artifact-bound
release metadata; this historical note proves none of them.
