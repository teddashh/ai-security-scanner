# Archived v0.2.0 product proposal

This file retains the useful product ideas from an unshipped proposal. It is not a current plan, milestone, or work queue. Current direction comes from the [product specification](../product-spec.md).

## Product ideas retained

- Use explicit repository, IaC, OCI image-layout, Kubernetes manifest, and node-configuration inputs instead of one ambiguous directory contract.
- Let the backend validate the selected target, create a bounded immutable snapshot, and expose only the declared mount and profile to each upstream scanner.
- Keep raw evidence, scanner provenance, coverage gaps, and the difference between empty, partial, failed, and untested work in one professional report.
- Bind cloud discovery and execution to one exact provider identity and resource boundary.
- Preserve upstream engine identifiers, evidence, severity, and remediation while keeping product explanation and prioritization in the shared report layer.
- Keep one unavailable scanner local to its task so completed sibling checks and saved evidence remain usable.
- Preserve cases and conservative comparison semantics when scanners, adapters, rules, inputs, or completeness change.

The proposal's setup funnel, fixed engine count, platform matrix, and distribution plan are discarded. They do not define product completeness. Beginner value is measured by reaching a real security result quickly, understanding what matters, and seeing what was not tested.
