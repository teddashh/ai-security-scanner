# v0.1.5 Windows launch and visible scan-activity pre-release

> **Historical / non-normative release-line record.** This file preserves claims and plans written for this version line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.5` was the Windows-first public preview that attempted to remove the repeated Ready/Repair
experience and make scan activity visible. Its remaining readiness-first wording is superseded:
the current workspace opens immediately, and task-specific scan-tool preparation/reconciliation
runs behind selected work rather than becoming a product state the user must clear.

## What feels different

- On first launch, the app checks what Windows prerequisites are already installed and prepares the
  private local scan tools automatically.
- If Windows itself needs a change, the app uses the normal Windows approval dialog. A required
  restart stays visible and under the user's control.
- A missing or invalid packaged component must never be executed. The current product first performs
  bounded automatic repair from a verified source; if none is available, only dependent tasks become
  unavailable and the app keeps projects, reports, unsigned exports, and unaffected work usable.
- The current Start path persists the run/tasks before dependency preflight. Activity therefore
  describes the selected user task and task-local preparation rather than a global readiness check
  that decides whether a run may exist.
- If updates take longer than expected, the app says so without pretending that a deliberately
  paused scan is stuck.

## One event log across every scan route

Website, external-IP, internal-network, source-code, infrastructure-as-code, cloud, container, and
Kubernetes checks now use the same activity model. The user sees one timestamped sequence instead
of having to infer progress from a spinner or open unrelated setup screens.

When an individual check cannot start, the event log names the useful next action and the master
report retains its exact coverage gap. Technical details keep a stable diagnostic code. Once the
user presses Start, a durable run exists before preflight, so a dependency failure is never reduced
to an opaque pre-run blocker. Redacted diagnostics include safe timestamps, statuses, phases,
versions, and counts while excluding target names, local paths, raw evidence, credentials, and raw
scanner output.

## Startup and control

First-launch preparation does not start a security scan. The app still waits for an explicit Start
action before contacting an approved target, and it does not add targets or widen the selected
scope. Existing local cases, evidence snapshots, cleanup obligations, and historical provenance
remain intact across the update.

## Historical testing status

This was a public testing pre-release on the way to `v0.2.0`. Its release pipeline built and
qualified the native installers and their packaged components. The macOS 15 Intel job verified the
installed app, its companion executables, and its packaged runtime manifest. Because the hosted Mac
could not run the required nested virtualization, the network-disabled Gitleaks container probe and
every runtime operation were recorded as `not_observed`, not passed.

That historical channel accepted this limited evidence only for a pre-release and planned to
require a real managed-runtime lifecycle on a suitable Mac for its stable release. Current
acceptance qualifies each exact artifact and claimed capability independently, with the
installed-Windows human path taking priority over modeled runtime checks.

The note's deferred formal QC/code-review sequence is historical and does not replace the current
human-path-first acceptance order.
