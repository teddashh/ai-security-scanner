# v0.1.8 Windows public testing prerelease

> **Release-specific, non-normative context.** This page explains what the v0.1.8 testing prerelease does and does not claim. The [canonical product specification](../product-spec.md) controls product behavior and release classes; current implementation gaps remain in the [product audit](../product-audit.md).

`v0.1.8` is a public testing prerelease, not a beginner-ready installer recommendation or stable
deployment. An exact Windows installer may be offered after its automated technical qualification
passes, with public provenance for those bytes and prominent per-installer disclosure that the
exact-candidate beginner path, real installed-app lifecycle, data-preservation path, or Authenticode
verification remains unobserved where applicable. This candidate line has no accepted generic
observation namespace and does not turn a modeled result into human or signing evidence. Those gaps
block beginner-ready/stable promotion, not honest public testing or an independently qualified Linux
or macOS artifact. Commit-bound QC artifacts remain bound to their source commit and checksums but
do not have a public GitHub artifact attestation. The current product direction removes
manual WSL cleanup in both ownership outcomes: verified product-owned disposable state is repaired
or rebuilt automatically, while uncertain state is preserved beside a new unique isolated runtime.

## What feels different

- The workspace opens while any earlier product-owned setup is reconciled in the background, with
  plain-language progress in English or Traditional Chinese.
- A verified product-owned workspace is preserved, replaced, and restarted automatically.
- If setup is interrupted, the app resumes from durable recovery records instead of asking the
  user to repeat the whole process.
- This historical draft expected a manual Windows path for uncertain ownership. That expectation is
  superseded by the canonical rule: preserve the uncertain workspace, create a new isolated runtime,
  and continue without asking a beginner to administer WSL.

## Superseded legacy recovery design

An earlier `v0.1.8` candidate proposed a version-specific WSL export/import/quarantine/unregister
transaction, ghost-migration receipts, permanent consumed markers, and exact legacy-manifest
coupling. That mechanism is removed from the product direction and must not be reintroduced from
this release note. It added a second recovery state machine and still stranded an ownership-unknown
beginner instead of restoring continuity.

The current rule is smaller: same-version Repair or upgrade may replace verified application
binaries and registration without inspecting or claiming runtime state. Verified product-owned
disposable runtime may be repaired/rebuilt automatically. A ghost registration, missing executable,
missing manifest, similar name, or otherwise insufficient ownership proof never authorizes runtime
mutation; the old object stays untouched while one new unique product-owned generation is created.
Retry/restart reuses its durable generation, and case data remains outside every runtime. Historical
v0.1.7/v0.1.8 manifest hashes are artifact evidence only, never name-based ownership or deletion
authority.

## Existing cases and export identity

A normal install-over-`v0.1.7` qualification must preserve the complete default application-data
snapshot, a real synthetic case, the existing local export-integrity private key byte for byte,
and its public Ed25519 signer identity. `v0.1.8` adopts that old key into a signed durable public
identity document. If the private key later disappears, the application does not silently create
a different signer; rotation requires an explicit command acknowledging the exact lost key ID.
That condition blocks only a requested signed export and immediately leaves an unsigned readable
export available; it never blocks scanning, reports, or reopening a project.

Exports now include one consolidated relationship report for NIST CSF 2.0, ISO/IEC 27001:2022,
and AIDEFEND 1.20260805. It keeps incomplete and unknown coverage visible and never represents a
relationship as an audit, certification, compliance decision, implementation score, pass, or
fail. AIDEFEND coordinates are not inferred unless the run was explicitly identified as an AI
system assessment or its selected artifact was explicitly declared AI-generated or materially
AI-modified.

## Superseded qualification plan

Earlier candidate work treated the removed export/import recovery transaction, its receipts, and
two NSIS-only fixtures as required promotion evidence. Those fixtures are not a current
implementation target and cannot justify rebuilding the retired mechanism. If retained for
historical diagnosis, they are supporting data-preservation observations only: their seeded CLI
HTML does not prove that the installed desktop completed a real `127.0.0.1:9001` scan, reopened the
project, and exported it. Current Windows acceptance follows the canonical beginner human path plus
focused N-1/Repair/uninstall fixtures for the actual simpler side-by-side lifecycle. MSI and NSIS
remain independently qualified artifacts, and missing evidence for one never gates a sibling.

Fresh Linux and Windows installer jobs exercise the managed runtime, fixed private gateway, and
network-disabled Gitleaks container probe. The fixed gateway probe exchanges only a SOCKS greeting
and never sends CONNECT. Windows MSI and Windows NSIS Setup are qualified independently.

The macOS 15 Intel job verifies the installed app, its companion executables, and packaged runtime
manifest. Its managed-runtime lifecycle and network-disabled Gitleaks container probe are recorded
as `not_observed`, not passed because the hosted environment does not provide the nested
virtualization required by AppleHV. This limited evidence is accepted only for a pre-release.

Apple Developer ID signing and notarization are not configured for this QC preview. Windows
Authenticode has not been independently verified. Technically qualified Windows installers may be
offered as public testing prereleases with that limitation stated; they are not presented as signed,
recommended, beginner-ready, or stable releases. Independently qualified Linux or macOS artifacts
remain eligible. The installed application updater consumes only signed AppImage, macOS app archive,
and Windows NSIS payloads; DEB, RPM, and MSI remain installer formats and are not advertised as app
updates. Supported updater payloads use the separate release signing key and must pass the checked-in
integrity verification.
