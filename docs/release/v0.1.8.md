# v0.1.8 Windows recovery candidate (not installable yet)

> **Historical / non-normative candidate snapshot.** This file preserves claims and plans written for this candidate line. It does not define current product behavior, release gates, recovery, consent, or installation advice, and it is not evidence that every described path shipped or passed. The [canonical product specification](../product-spec.md) controls; current implementation gaps are tracked in the [product audit](../product-audit.md).

`v0.1.8` is still under Windows qualification. No tag or public release exists yet, and the
current source commit must not be treated as an installer recommendation. A main-branch manual
preflight may produce a commit-bound QC artifact, but tag publication is fail-closed until Windows
Authenticode signing and verification are configured. That workflow artifact is bound to the
source commit and checksums, but it does not have a public GitHub artifact attestation. The candidate is meant
to remove the manual WSL cleanup step shown during first launch when ai-security-scanner can prove
that the old scan-tool workspace belongs to this product.

## What feels different

- First launch explains that it is finishing an earlier setup and shows live progress in English
  or Traditional Chinese.
- A verified product-owned workspace is preserved, replaced, and restarted automatically.
- If setup is interrupted, the app resumes from durable recovery records instead of asking the
  user to repeat the whole process.
- Manual Windows instructions remain only for a workspace whose ownership cannot be proven. The
  app does not remove that workspace.

## Recovery transaction

Before replacing anything, the app uniquely binds the WSL distribution to a verified installed
ai-security-scanner manifest and its private storage. It checks free space, terminates that exact
distribution, performs a full file proof, exports a tar recovery archive, synchronizes it to disk,
and records its size and SHA-256. The archive is imported under a generated isolated distribution
name and verified against Windows' registration and storage state.

Only after the archive, imported recovery workspace, and unchanged original registration have all
been reverified may the old distribution be unregistered. The replacement runtime is then created,
started, and required to become ready before the temporary bootable recovery distribution is
removed. The opaque archive and bounded recovery records remain available for diagnosis. Cleanup
and retry paths are idempotent across process or machine interruption.

The recovery phase does not broaden scan scope, approve a target, or contact a scan target.

## Exact v0.1.7 ghost-install migration

The one automatic legacy path is limited to the public Windows `v0.1.7` release. It does not claim
a WSL distribution from its name alone. The verifier binds the retained registration and storage
to the exact old managed-runtime manifest and machine-image digests, the exact private provider
layout and configuration, a valid product-created SSH identity, the exact HKCU NSIS product
history, and the physical WSL registration path and VHD. A missing or different signal fails
closed and leaves the workspace untouched.

The candidate installer handles the narrower state in which Windows still records `v0.1.7` but
both the old application and uninstaller are gone. It restores the application without deleting
the retained data or WSL state and writes a version-bounded transition receipt. The application
requires that receipt after installation before the legacy recovery proof can authorize the
existing export, quarantine, verification, and replacement transaction. The exact receipt is
copied into the durable recovery intent before it is atomically consumed from HKCU. Interrupted
work can resume only from that matching intent. Once the replacement is ready, the application
writes a permanent no-follow, single-link, current-user-owned, owner-only consumed proof at
`wsl-recovery/ghost-migration-consumed-<machine>.json`; it binds the recovery ID, receipt, exact
v0.1.7 provider manifest, candidate manifest and image, machine, and distribution before the
pending transaction is removed. A fresh `v0.1.8` installation has neither the receipt nor that
bounded proof and cannot use or replay this migration path.

The product-side management contract is now an explicit immutable manifest input rather than an
assumption hidden behind unchanged Podman files. The public v0.1.7 Windows schema-2 manifest is
`8b2257ace33ecb14bb0995044a4e6d2b4e71b314741601122801fbb59e7de13f`. The v0.1.8 bundle uses schema 3,
management contract revision `2026-08-29.1`, and the reviewed Windows manifest identity
`a8112473e5d87655e6145ea5f6cff569c872329d2ec14bfb9463078abcb60e3a`. The upstream Podman client,
helper, and WSL machine-image size/digest pins are unchanged; the new identity records the changed
ownership/recovery behavior. A v0.1.8 binary rejects schema 2 as its current bundled resource while
still allowing the exact old installed manifest to be verified for the bounded N-1 transaction.

## Existing cases and export identity

A normal install-over-`v0.1.7` qualification must preserve the complete default application-data
snapshot, a real synthetic case, the existing local export-integrity private key byte for byte,
and its public Ed25519 signer identity. `v0.1.8` adopts that old key into a signed durable public
identity document. If the private key later disappears, the application does not silently create
a different signer; rotation requires an explicit command acknowledging the exact lost key ID.

Exports now include one consolidated relationship report for NIST CSF 2.0, ISO/IEC 27001:2022,
and AIDEFEND 1.20260805. It keeps incomplete and unknown coverage visible and never represents a
relationship as an audit, certification, compliance decision, implementation score, pass, or
fail. AIDEFEND coordinates are not inferred unless the run was explicitly identified as an AI
system assessment or its selected artifact was explicitly declared AI-generated or materially
AI-modified.

## Required release qualification

The recovery state machine has Rust regression coverage for first attempt, interrupted import,
interrupted replacement, durable retry, exact cleanup, and direct-unregister authorization. The
frontend has bilingual progress and fallback coverage. The Windows production and test code paths
are compiled with warnings denied.

Before an installer can be offered, two separate Windows NSIS qualifications must pass against the
same candidate bytes:

1. A normal installation of the immutable public `v0.1.7` installer is upgraded in place. The
   test verifies the replacement executable and uninstaller, exact HKCU transition receipt, full
   application-data preservation, case readability, and signing-identity continuity.
2. A real `v0.1.7` managed WSL machine is installed, started, stopped, and converted into the exact
   reported ghost state by removing only the old versions payload and the two missing installer
   files. The candidate installer and runtime must then recover it automatically without the
   manual-action fallback, preserve the case and signer, prove every recovery receipt and archive,
   prove HKCU no longer contains the transition receipt, retain the exact protected permanent
   consumed marker through runtime purge and NSIS uninstall, and clean up only the exact
   qualification workspace.

Both records are bound to the prior installer hash, prior runtime and machine-image hashes,
candidate installer hash, candidate runtime identity, and source commit. Release finalization must
reject a missing, malformed, mutated, or mismatched record.

Fresh Linux and Windows installer jobs exercise the managed runtime, fixed private gateway, and
network-disabled Gitleaks container probe. The fixed gateway probe exchanges only a SOCKS greeting
and never sends CONNECT. Windows MSI and Windows NSIS Setup are qualified independently.

The macOS 15 Intel job verifies the installed app, its companion executables, and packaged runtime
manifest. Its managed-runtime lifecycle and network-disabled Gitleaks container probe are recorded
as `not_observed`, not passed because the hosted environment does not provide the nested
virtualization required by AppleHV. This limited evidence is accepted only for a pre-release.

Apple Developer ID signing and notarization are not configured for this QC preview. Windows
Authenticode is also not configured, so public tag publication is deliberately blocked rather than
presenting an unsigned Windows build as a release. Updater payloads use the separate release
signing key and must pass the checked-in integrity and provenance workflow.
