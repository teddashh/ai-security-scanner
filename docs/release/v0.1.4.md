# v0.1.4 actionable scan-flow pre-release

`v0.1.4` is the installable public preview that fixes the failed 0/0 home-network experience found
during hands-on testing. It replaces a scanner-first setup maze with one guided path for each thing
you want to check.

## What feels different

- Choose a home or office network, website, external IP, source code, infrastructure as code, cloud
  account, container image, or Kubernetes configuration. The app shows only the setup that use case
  needs.
- The installed app can suggest one safe private subnet from local network settings. It does not
  probe the network or silently choose a target; you accept the suggestion with one visible click.
- Home-network and external-IP checks start with a useful, bounded common-service preset. Website
  checks keep the exact protocol and port you entered. Advanced options are still available.
- One clear confirmation covers the selected target and scan activity. The app no longer spreads
  that decision across unrelated or hidden controls.
- When a case has more than one account from the same cloud provider, the quick confirmation is
  available only for the exact account that discovered the selected target. The app never treats two
  AWS, Azure, Google Cloud, or Microsoft 365 sign-ins as interchangeable.
- If no scanner can actually run, no run is created. The same applies when the private scan tools
  are not running or a cloud account's short-lived connection has expired or lacks enough uses for
  the exact plan. You stay in setup with one useful next action instead of receiving a failed 0/0
  result or the same setup failure repeated for every tool.
- Local project copies, saved read-only sources, the packaged private-network helper, and evidence
  needed to continue an interrupted scan are checked before any new or resumed run state is saved.
  Missing or changed evidence leaves the earlier result untouched and tells you to start a fresh
  scan; a storage or worker problem is reported separately instead of blaming your target setup.
- Setup and run failures can produce a downloadable redacted diagnostic with technical statuses,
  error codes, versions, and counts, but no target names, local paths, raw evidence, or scanner text.
- Scan progress names the number it actually measures: targets that finished every applicable
  check, rather than incorrectly calling that number a count of scanner checks.

## Shared behavior across every scan route

The execution planner now checks the saved use case, target kind, protocol, exact permission, local
tool readiness, short-lived provider capability, and engine compatibility before persisting a run.
For cloud scans, it atomically reserves the capacity and backend-only credentials needed by the
entire exact plan before a run is saved. Another scan, reconnect, or revoke cannot take that capacity
between the check and worker dispatch. Storage or worker-start failure releases the reservation; the
worker remains inactive until the reservation is committed. Expired, insufficient, ambiguous, or
mismatched connections therefore stay out of the scanner fanout and lead to one specific next step.
Only applicable engines receive compatible, authorized targets. The same pre-persist behavior covers
a first scan, verification scan, and resumed desktop scan rather than being a page-specific workaround.
The worker repeats every local integrity check immediately before use, so a file changed after the
first readiness check cannot be silently accepted.

Local source-code, IaC, container, and Kubernetes routes now use real immutable snapshots created by
the backend; questionnaire text is never presented as a scan target. Cloud setup starts with the one
provider selected for the case. Website, external-IP, and internal-network routes keep distinct
target and protocol behavior while sharing the same readiness contract.

## Windows setup

The one-click WSL 2 preparation introduced in `v0.1.3` remains part of this build. When Windows needs
an optional component or update, the app requests the standard administrator confirmation, invokes
the fixed Windows-owned operation, checks the result, and explains whether a restart is required.
Manual Microsoft commands remain available as a fallback.

## Testing status

Linux and Windows fresh-host qualification must install the product, install and start the managed
runtime, run the fixed isolated Gitleaks container probe, stop, uninstall, and prove cleanup.

The macOS 15 Intel job must verify the DMG, app layout, all companion executables, packaged runtime
manifest, CLI, desktop startup, and cleanup. GitHub-hosted macOS does not provide the nested
virtualization required by the AppleHV managed machine. The network-disabled Gitleaks container probe
and every runtime operation are therefore recorded as `not_observed`, not passed.

This limited evidence is accepted only for a pre-release; a stable release still requires a real
managed-runtime lifecycle on a suitable Mac.

This remains a public testing pre-release on the way to `v0.2.0`. Formal QC and code review remain
scheduled after the product workflow has been exercised end to end, as planned.
